## 2. Minha leitura disso, direta

Você tinha razão em suspeitar que havia conhecimento comercial real por trás das decisões de taxonomia (intents/competências/categorias de decisão) — a disciplina "KNOW ≠ APPROVE ≠ COMMIT" e as fronteiras finíssimas entre `desconto`/`condicao_pagamento`/`financeiro_booking` claramente vêm de ter visto casos reais confusos. **Mas esse conhecimento foi absorvido só como ESTRUTURA (taxonomia, rótulos, regras de gate) — nunca como CONTEÚDO DE ESTRATÉGIA comercial** (o que fazer, não só como classificar). É exatamente a distinção que você fez no ponto 6 do seu pedido: "não confundir um documento existente com conhecimento efetivamente disponível para o modelo durante uma conversa" — aqui o caso é o oposto: a ESTRUTURA está disponível e em produção, mas o CONTEÚDO estratégico nunca existiu, nem como documento.

A fundação mais valiosa que já existe pra construir o Playbook sem duplicar nada é exatamente a arquitetura que você descreveu no ponto 5 (4 camadas) — ela já está parcialmente implementada, só com nomes diferentes:

## 3. Proposta — Playbook DJ/Música (como conteúdo, não arquitetura nova)

**Minha recomendação central:** não criar um "módulo Playbook" novo que o Planner consulta via tool call (isso seria exatamente a "arquitetura paralela" que você pediu pra evitar, e adicionaria latência/chamadas extras). Em vez disso, o Playbook é **conteúdo versionado** (um arquivo TypeScript de constantes, mesmo padrão de `decision-categories.ts`/`competencies.ts`) que alimenta **uma seção nova e pequena dentro do prompt já existente do Planner** (`buildPlannerInstructions()`), condicionada ao `Competency` já roteado — isto é, reaproveita o Competence Router que já existe (`routeCompetencies`) em vez de duplicar a decisão de "quando isso se aplica".

Estrutura proposta, concreta:

- **`src/lib/intelligence/playbook/dj-musica.ts`** — constantes de conteúdo (nunca prompt livre): tipos de evento (club/festival/privado/corporativo/ativação/cultural) com suas características relevantes; sequência possível de contrato→nota→sinal→saldo (como princípio, "podem seguir ordens diferentes", nunca uma ordem fixa imposta); heurística de quando pedir orçamento antes de apresentar cachê (ex.: evento corporativo/ativação de marca → sempre perguntar orçamento antes; club recorrente já conhecido → cachê direto é aceitável). Cada item com uma frase curta de PRINCÍPIO (não resposta decorada), seguindo exatamente o formato que você pediu no ponto 4 (o que já sabemos / qual o objetivo comercial / o que preserva a oportunidade).
- **Injeção no prompt**: `buildPlannerInstructions()` ganha um parâmetro opcional `competencies: Competency[]` (já calculado por `routeCompetencies`, reaproveitado — zero chamada nova). Quando `comercial_negociacao` ou `producao` estão presentes, concatena só o bloco de Playbook relevante — nunca o catálogo inteiro, sempre a fatia que já se provou necessária pela classificação real desta mensagem. Isso resolve diretamente sua preocupação do ponto 6 ("evite prompts gigantes") — o prompt cresce só quando o assunto é comercial, nunca pra uma pergunta de suporte.
- **Rider como princípio, não regra binária**: em vez de "regras de rider", um parágrafo curto no Playbook: "rider expressa preferência técnica do artista, nunca exigência incondicional — avalie porte/natureza do evento e estrutura disponível antes de tratar uma divergência como bloqueio; quando a estrutura disponível diverge do rider padrão, pergunte ao artista antes de recusar ou aceitar automaticamente." Isso é 3 frases, não um motor de regras — compatível com "princípios de decisão, não respostas decoradas".
- **Múltiplos interlocutores por booking**: esta é a única peça que PRECISA de mudança estrutural real (não cabe só em prompt) — o Booking Context hoje (`opportunity`/`booking` sections) não distingue contratante/produtor/financeiro/autorizado-a-decidir. Isso é trabalho de Context Builder (nova seção ou campo), não de Playbook — registro aqui como dependência, não tento resolver escondido dentro da proposta de prompt.

## 4. Memória comercial aprendida — ligar o protótipo que já existe

Em vez de desenhar um sistema novo, **ligar `memory-policy.ts` ao Context Builder** (exatamente o próximo passo que o próprio comentário do arquivo já previa). Trabalho concreto, sequenciado:
1. Migration nova: tabela `professional_memories` espelhando `ProfessionalMemory` (mesmo padrão de toda migration desta sessão — aditiva, nunca altera schema existente).
2. Wrapper RPC-based (mesmo padrão `AnySupabaseClient` já usado em `professional-contact-memories.ts`/`ai-harness-lease.ts`).
3. Nova seção `ContextPackage.professionalMemories` no Context Builder, chamando `selectContextMemories` (lógica pura já pronta e já testada) sobre as linhas reais do banco.
4. `proposeMemory` chamado a partir de onde já faz sentido: quando o Planner identifica `treinamento_profissional` (intent que já existe!) ou um padrão comercial repetido — sempre como PROPOSTA, nunca auto-aprovada (a disciplina já está no módulo).
5. Aprovação: UI simples (mesmo padrão de `/admin`), profissional revisa e aprova/rejeita.

Isso é reaproveitamento total — zero arquitetura nova, só ligar o que já foi desenhado e testado.
